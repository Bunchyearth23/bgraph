## 2. Findings per case, with the measurement

Text legibility was measured two ways, never by eye alone: (a) vector geometry from
`bgraph … --json` plus real Archivo glyph advances taken from the installed
`/usr/local/share/fonts/a/Archivo_*.ttf` with fontTools, and (b) the rasterised PNG
(`resvg`), where the dark ink pixels are counted directly. Circle geometry is the
JSON `nodes[].rect`; areas use the same lens formula the renderer uses.

### 2.1 Three sets — the shipped gallery example (`examples/venn.bd`)

* **Areas exact.** A∩B lens 9896.02 px² vs 9896.02 required, A∩C 11545.35 vs
  11545.35, B∩C 5772.68 vs 5772.68 — all three within 1e-6 relative.
* **Key clean.** No text–text overlap, no text outside the canvas, key column starts
  36.0 px right of the widest circle edge, values right-aligned in one column at
  x = 576.1, chip letters fully inside their chips (0 ink pixels outside, pixel
  count).
* **One defect.** The letter **C** is drawn *inside circle A*: its ink is 29.9 px
  inside A's outline (pixel measurement; the vector model agrees at 30.1 px). A
  reader cannot tell whether "C" labels the green circle or the blue∩green overlap,
  because the letters carry no colour of their own (`ink(&base, &theme)` for every
  letter, `src/charts.rs:1274`).
  *Why:* C's exclusive region is only **17.1 %** of its circle (2540.8 px²), and the
  maximum exclusive clearance available is **15.28 px** against the required
  `font + 3 = 15 px`. The 33×33 sampling grid in the placement search
  (`src/charts.rs:1337-1338`) steps over that crescent, so the code falls back to
  `exclusive = false` and drops the letter into the overlap. Reproduced by
  re-running the placement search at higher resolution: at half-steps 24 the same
  data yields an exclusive C at 15.03 px from A's outline, at 96 half-steps 15.28 px.
  The same data with the default `radius: 110` and the default font (13) has only
  16.01 px of exclusive room against a required 16 px — a knife edge that no grid
  can win comfortably.

### 2.2 Two sets — `type venn`, 420 / 260, `a -> b 120`

Lens 10860.93 px² = 10860.93 required — exact. Both letters are exclusive, ≥ 29.5 px
from any outline (pixel: +29.1 px). Key shows one "A and B" row. No "indicative"

### 2.3 Containment — 420 / 260, `a -> b 250`

### 2.4 Identical circles — 300 / 300, `a -> b 300`

d = 0.00, lens 38013.27 = 38013.27 exact. Both letters land in the one circle

### 2.5 Empty set — 300 / 0

### 2.6 Long names, mixed fonts — 12 px / 19 px, 3-line wrap

### 2.7 Disjoint sets — no links

### 2.8 Genuinely infeasible distances — `a -> b 0`, `a -> c 0`, `b -> c 70`

The three distances do form a triangle here, so the exact branch is used and all three

### 2.9 Dark surface — background `#0b1120`

All three lenses exact; the letters and key are light-on-dark (`#e2e8f0`) and the key

No text overflows the canvas in any of the ten fixtures; no key entry overlaps
another; every chip letter is inside its chip; the value column is a single

## 3. The two defects the automated checks do not catch

### 3.1 A letter that lands in an overlap is ambiguous (§2.1)

Technically valid — the crate's own test asserts only that the letter does not
*cross* an outline, and it does not — but hard to read. **Needs a change in
`src/charts.rs`, not in `src/math.rs`** (the geometry is exact; the search that
places the letter is in `charts.rs`). Diff A below: after the coarse 33×33 sweep,
refine locally around the best sample so a narrow exclusive crescent is not missed.
Simulated against the crate's own three test sources and the gallery file: all
assertions still hold, and the gallery's C becomes exclusive at 15.29 px.

**Consequence, verified:** both diffs were applied to a scratch copy of the repository
(`/tmp/w171check`, never to the shared worktree), the crate was rebuilt there and the
Venn suite re-run: `running 7 tests` … `test result: ok. 7 passed; 0 failed` — all
seven still pass, including `venn_circle_keys_clear_the_outlines_and_each_other`.
Re-rendering the shipped gallery file with the patched renderer moves the letter C
from **(144.1, 248.8), inside circle A**, to **(201.6, 281.7), inside no other
circle**, 15.29 px clear of A's outline — the green-only crescent at the foot of the
green circle. The rendered PNG confirms it by eye.

The `venn` golden therefore moves: the golden test fails with the new hash printed —
**`venn d7917ca1e1b25c46`** (was `venn be043a9c49825e07`). So `docs/goldens.txt` must
be updated with that line and `examples/venn.svg` regenerated
(`checked_in_examples_match_init_and_rendered_svg` compares it byte for byte). Both
files are outside this session's ownership.

### 3.2 A contradictory Venn is accepted, and the picture then contradicts the key

Fixture: 420 / 260 / 180 with `a -> b 0`, `a -> c 180`, `b -> c 180` — i.e. all of C
is in A and all of C is in B, yet A and B share nothing. `check` accepts it (only the
three-set warning). The renderer cannot satisfy it, falls back to the schematic
arrangement, and draws a picture whose key says **"A and B = 0"** while the blue and
orange circles visibly overlap.

Measured on the rendered PNG: the drawn A∩B lens is 9112.3 px² ≈ **100.7 people**,
A∩C 6440 px² ≈ 71.2, B∩C 3340 px² ≈ 36.9 — against key totals of 0 / 180 / 180.

The data is contradictory, not merely hard to draw: |A∩B| ≥ |A∩C| + |B∩C| − |C| =
180 + 180 − 180 = 180. The honest response is a diagnostic, and by the project's own
pattern it belongs in `check.rs` (validation in `check.rs`, never in the layout).
Diff B below adds that rule.

**This rule also makes one shipped test source an error:**
`set a 100 / set b 100 / set c 100 / a->b 99 / a->c 99 / b->c 1` — the same bound
gives |B∩C| ≥ 98. `venn_degenerate_sets_keep_finite_geometry_and_readable_keys`
renders that source today, so it must lose that line or the rule must become a
warning (a one-word change: `Diag::error` → `Diag::warn`). The exact replacement
source list is in §6. **Verified in the scratch copy:** with that one source removed
from the list, the suite is `7 passed; 0 failed`.

## 5. `src/math.rs` — no change needed

Nothing in the Venn path needs a math fix: the lens areas are exact to better than
1e-6 relative in every feasible case measured, the bisection in `distance_for` is
monotone and deterministic, the rendering is byte-identical across repeats, and the
Venn path already goes through the portable kernels (`crate::math::acos`,
`crate::math::hypot`) that `src/math.rs` exists to provide. The two defects above are
a *search* problem (`charts.rs`) and a *validation* problem (`check.rs`). `src/math.rs`
was therefore left untouched.

## 7. User-facing validation checklist (use as the acceptance list)

For each Venn picture, open the SVG at 100 % zoom and check, in this order:

1. **One letter per circle, in the right circle.** The letter for a set must sit in
   the part of that circle which no other circle covers (the blue-only crescent for
   A, the orange-only area for B, the green-only crescent for C). *In the shipped
   gallery example, C does not: it is in the blue∩green overlap (29.9 px inside the
   blue outline). Expected after Diff A: C in the green-only crescent.*
2. **No letter touches an outline.** Every letter has clear space on all sides
   (measured ≥ 9.8 px in every case checked).
3. **No bare numbers inside the circles.** The circles carry only A, B, C; every
   number is in the key.
4. **The key reads top to bottom.** "Set totals" → three rows, each with a coloured
   chip holding its letter, the set name (wrapped if long) and the total
   right-aligned in one column.
5. **Chip letters are inside their chips**, and the chip colour is the circle's
   colour (blue = A, orange = B, green = C in the default palette).
6. **Names never touch the numbers.** A wrapped name may run to several lines; the
   number must stay clear of it and in the same column as the other numbers.
7. **"Shared members" names each pair** ("A and B", "A and C", "B and C") with its
   number in the *same* right-aligned column as the set totals; no number is left
   floating next to a circle.
8. **The two grey notes are present** for a three-set diagram: "Pair totals include
   the third set." and "Three-set areas are indicative." A two-set diagram must
   **not** carry them.
9. **Zero means zero.** If a pair total is 0, the two circles must touch or be
   apart — never overlap. *Today this can fail when the three pair distances
   cannot form a triangle (Diff B): the picture shows an overlap beside a key that
   says "A and B = 0".*
10. **An empty set has no circle** and keeps only its key row.
11. **Sanity of the totals**: a pair total can never exceed the smaller of the two
    sets, and if one set is entirely inside two others, those two must share at
    least that set's count.
12. **The colours**: blue/orange/green in the default palette, and the drawing sits
    on a light surface (the gallery example is deliberately white).
