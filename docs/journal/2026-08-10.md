## `W-037` — `label-offset`, the escape hatch out of automatic label placement

**What.** A `label-offset` property (alias `text-offset`), valid on both nodes and edges, taking two
numbers in user units — positive right and down, the second optional.

- `src/props.rs` — the two `PropDef`s, so `check`, completion and `docs/reference.md` all learn it
  at once
- `src/style.rs` — `label_offset: Option<(f64, f64)>` through the cascade, parsed in the one
  `apply_prop` arm the convention asks for
- `src/render_svg.rs` — six sites: `place_label`, the pin, `bounds`, `group_frame`, `node_label`
- `src/tests.rs` — four tests: the pin holds, a moved label still displaces the next one, the
  viewBox follows a label moved outside its shape, and the property cascades like any other
- `docs/language.md` — a *Moving a label* section with two examples, both parsed and rendered by
  the suite (`X-015`)
- `docs/reference.md` — regenerated from the tables

**Why.** `X-006` says edge labels avoid lines, not each other's readability, and that the solver is
local: nothing guarantees the best global arrangement. On a busy diagram it runs out of room. The
answer taken here is an escape hatch rather than a better cost function — the author can see what
the cost function cannot, and a declared position is a decision. Hence the pin: on an edge, an
offset stops the avoidance from second-guessing it, so the label does not drift when a neighbouring
edge changes.

**Impact.** `X-006` stays `mitigated` and now names its escape hatch. No behaviour changes for a
file that does not use the property; the SVG for every example is byte-identical.

## Two chantiers carried an undecided design — decided before starting

Preparing the work order surfaced that `W-047` and `W-045` were not chantiers but questions wearing
a chantier's clothes. Both were settled by looking at the code rather than at taste.

**`D-024` — an activation bar is a block.** `activate api { … }` is a `group` whose `edge_members`
are the messages the bar spans. The mechanism was already built and already right: a group records
`members` **and** `edge_members`, and a sequence frame spans message *rows* — which is exactly a
bar's extent. Nesting comes free. The alternative, inferring a bar from a call and its matching
reply, was refused because "matching" is a guess the moment two calls are in flight, and a silent
guess is what `D-005` exists to prevent.

**`D-025` — a pin is a member line, a wire carries its pins as positional data.** `- 1: +12V` is
`W-013`; `j1 -> j2 "power" 1 3` is `W-015`. No grammar moves.

The dotted form `j1.3` was the obvious answer and it is wrong for a reason worth writing down:
`ident` forbids `.` and `3` is not an identifier, so `j1.3` does not parse at all — but `j1.p3`
**does**, as `ident` + `class_ref`. The most readable syntax available is the one that already means
*a class reference*. Choosing it would have bought a pretty example and an ambiguity in both
grammars.

## `W-048` — true scatter for `type xy`, and the mechanism `D-023` promised

`type xy` now answers to two words. `series north 4 8 15` spreads its numbers evenly across the axis,
as it always did; `scatter north 1 4 3 8` reads them **two at a time** as coordinates, so the x
written is the x drawn.

**The mechanism, not just the feature.** `ArchetypeDef` gained `alt_items: &[AltItem]` — a second
word with a positional shape of its own — plus `accepts`, `slots_for` and `items`. Nothing dispatches
on arity anywhere: the word decides, which is the whole of `D-023`.

Neither grammar moved, as predicted: `item_keyword` is `$.identifier` in tree-sitter and `ident` in
pest, so a new keyword is not a new token. `xy` also needed its own `XY_ITEM_PROPS`, because
`SERIES_ITEM_PROPS` is shared with `bar` and a bar has no x axis to put a pair on.

**The dangerous part was the thirteen call sites.** `node.effective_props(def.slots)` reads the
archetype's *primary* form. With a second form in play, every one of them would have folded a
scatter's coordinates into `points` — and drawn a wrong plot with no error at all, since both are
lists of numbers. They now go through `NodeDecl::props_for(def)`, which resolves from the written
keyword. It takes the whole `ArchetypeDef` rather than a slot list on purpose: a caller cannot reach
past it. Same shape of fix as deleting `relevant_here` — make the wrong thing unsayable.

**Three judgement calls, all in `check`.**

- Mixing `series` and `scatter` in one plot is **refused**, not blended. One takes x from a mark's
  position in the line, the other from the numbers written; sharing an axis would give x two meanings
  and no reader could tell which applied to which mark.
- An odd count of coordinates is an **error**. The last x has no y, and silently dropping it would
  draw a plot missing a point the author wrote.
- A scatter draws **dots by default**, and `mark: line` sorts by x before drawing. Joining scattered
  points claims a continuity the data does not have, and a polyline in declaration order doubles
  back — which reads as data running backwards in x.

Eight tests, an `examples/scatter.bd`, a *second word for a second shape* section in `language.md`
(parsed and checked by the suite, per `X-015`), and the manual regenerated.

`D-023`'s own wording was corrected while doing this: it illustrated the rule with `point`/`pair`,
which are `quadrant`'s vocabulary. The real words are `series`/`scatter`. A decision whose example
does not exist is a decision nobody can check.

## `W-039` — `type bytefield`

Seventeen archetypes now. `bytefield` is `packet` read one order of magnitude up: the ruler counts
bytes, `width` defaults to 16 (a hex dump's width, not a packet's 32 bits), the ruler steps by four
rather than eight, and a field's range is `bytes` rather than `bits`.

**Written once, not twice.** `packet()` became `packet_like(…, Granularity)`, with `packet` and
`bytefield` as two thin entry points. Everything that makes the archetype work — splitting a field
across a row boundary, naming only its first segment, the range in the corner — is the same picture
at a different scale, and a second copy would have been a second place for the two to drift. Same for
`check_packet`, which takes the archetype name and reports in its own unit: a message about `bits` in
a byte diagram would send the author to a property that does not exist there.

`bytes` is a **separate** property from `bits`, not a reuse. The two are indistinguishable by value —
only the archetype knows which unit was meant — so keeping them apart makes writing the wrong one an
unknown-property error naming the genre that reads it (`D-022`). Both tested in both directions.

`examples/bytefield.bd` is the ELF64 header: exactly 64 bytes, four rows of sixteen, which is the
case a byte diagram exists for.

## `W-051` — `type requirements`, and a hole it made visible

Eighteen archetypes. A requirements view is a `class` box — a name over a ruled list of member lines,
placement still declared — plus the SysML relation vocabulary: `derive`, `satisfy`, `verify`,
`refine`, `trace`, `copy`, written positionally and drawn in guillemets on the line. `risk` and
`verify` say how likely a requirement is to go unmet and how it will be shown to be met.

`risk` is **drawn, not coloured**. Risk is ordinal and the categorical palette would imply it is not
— and the rule against adding a hue by eye exists for exactly this temptation.

Two warnings, because both halves of this genre can be silently empty and both are the failure it
exists to make visible: a relation with no link kind is a line whose meaning the reader has to guess,
and a requirement with no `verify` is one nobody has planned to check.

**`compartments` became a fact about the archetype.** The layout decided whether to rule off member
lines with `item.name == "class" || item.name == "er"` — a hand-written list, which is the shape of
thing nobody remembers to extend, and which `requirements` would have joined silently by not being
in it. It is `ArchetypeDef::members` now, and a test pins which genres carry it.

### The hole

`check_edges` validated `edge.props` — the **inline block only**. Positional edge data is folded into
named properties by `effective_props`, and that folded form was never checked. So `a -> b nonsense`
went through `check` untouched, in `er` as well as here: `one many` was validated, `nonsense` was
not. It reached `style.rs`, which bails without a span for a cardinality and not at all for a word
nothing parses.

That is `D-005` broken in the *idiomatic* form — positional data is the way these are meant to be
written. `check_edges` validates the folded props now, and the `er` case has a regression test of its
own.

## `W-050` — `type kanban`

Nineteen archetypes. Columns are `group`s in declaration order; cards stack inside them in
declaration order. The archetype places everything rather than leaving it to anchors — a board whose
columns had to be `right-of` one another would be busywork with nothing gained in the reading, and
`W-011` already supplies the membership.

**A column carries a `limit`, and `check` reports one that is over it.** That is the whole reason
this genre exists rather than being a `free` diagram with boxes in rows, so it is the diagnostic the
work was for. The header draws the tally against it — `In progress  3/2` — where a reader is already
looking. `examples/kanban.bd` ships one column deliberately over its limit, because the warning
firing is the point.

Two smaller judgements. A card outside every column is an **error**, not a stray box: a board with a
card nowhere is a board that is lying. And `limit` has to be `Ctx::Node` to be accepted on a group at
all, so it is also accepted on a *card*, where it means nothing — said out loud rather than ignored.

**`limit` rides the cascade**, so `check` resolves group styles (`resolved_groups`) rather than
reading raw props. Reading the props would have worked for every example in the repo and missed a
limit supplied by a class — the shape of gap that stays quiet because the common case works.

## `W-052` — `type journey`

Twenty archetypes. Steps in the order they are taken, one line per actor, `group`s as the sections
banded above the steps they hold.

The shape is borrowed rather than invented: scores are positional against `actors` exactly as `bar`'s
points are against `categories` (`W-016`), the lines and marks are `xy`'s (`W-017`), the frame and
legend are `W-012`'s, and the sections are the same `group` machinery kanban's columns use. What is
new is only that the two are read together — the point of a journey is the step where two people
diverge, which needs both lines on one axis.

**The axis is labelled at every whole score**, not by `nice_scale`. A satisfaction score has no
meaning between two of them, so a tick at 2.5 would be an axis making a claim the data cannot.

Three warnings, all about a picture that would otherwise quietly under-report: a step with fewer
scores than there are actors leaves a gap in someone's line, a file with no `actors` draws nothing at
all, and a score off the scale is clamped rather than silently rescaling the axis.

## `W-046` — `type radar`

Twenty-one archetypes. Axes clockwise from the top, one closed filled polygon per series.

It **reuses `bar`'s words verbatim** — `series` and `categories` — rather than inventing `axes` for
the same idea. A radar's axes *are* the named slots the numbers line up with; a synonym would have
cost a word of vocabulary and bought nothing but two ways to say one thing.

Two decisions that are both about the chart not lying, since this is the chart most often made to:

- **One scale for every axis.** Per-axis normalisation would make the shape — the only thing a reader
  actually compares — meaningless, because a ring would mean something different depending on which
  way you were looking.
- **Rings start at zero** unless `range` says otherwise. Starting them at the smallest value in the
  data exaggerates every difference, which is the standard way a radar flatters whatever it is
  describing.

Rings are drawn as the same polygon the data uses, not as circles: a circle would suggest a continuum
between axes that does not exist.

### The guard that caught me

`each_data_property_belongs_to_exactly_the_genres_that_read_it` failed the moment `radar` started
reading `points` — and in failing, showed that six properties added earlier today (`bytes`, `pairs`,
`scores`, `limit`, `risk`, `verify`, `link`) had never been added to its table. The mapping is
asserted rather than eyeballed precisely so that a genre quietly acquiring a property is a test
failure. It did its job.

## `W-044` — `type rack`

Twenty-two archetypes. A numbered frame, devices occupying inclusive spans of units.

**Units count from 1 at the bottom.** That is the one thing this archetype can get wrong in a way
that still looks right: a rack labelled top-down is correct about everything except where to put your
hands. It has a test of its own for that reason, and every unit is numbered on the rail rather than
every fifth — the number is what you count against while holding a server.

The interesting decision was in `check`, and it is where `rack` and `packet` part company despite
being the same picture rotated. A packet with unassigned bits **does not add up**; a rack with empty
units **has room**. Same shape of gap, opposite meanings — so gaps warn there and are silent here.
What is an error is what is physically impossible: two devices sharing a unit, or a device reaching
past the top of the frame.

## `W-047` — activation bars, and why the word had to be new

`D-024` settled the design; building it turned up the reason the decision was right for a sharper
reason than the one written down.

`activate api { … }` cannot be spelled `group api { … }`, because **a group id and an item id share
one namespace** — `check_groups` errors on exactly that collision. So `activate`'s identifier has to
be a *reference*, not a declaration, and that is a different statement even though it has the same
shape. Hence a second keyword in both grammars rather than a property on a group.

Everything downstream followed from that one distinction, and one place got it wrong first: every
message touching the activated participant was reported as "`api` is a group; edges connect items,
not frames". The fix is `frame_names`, one helper that answers *which ids name a frame* — so no
caller has to remember that an activation is not one.

The bar is a thin `PlacedNode` pushed after the lifeline, not a `Guide`: guides draw beneath
everything and this has to sit on top of the line it covers.

Both grammars moved, so the parser is regenerated, a corpus case is in `tests/grammar/accept`, and
the Zed queries learned the new word — `highlights.scm` gained `"activate"`, and `outline.scm`
captures the `keyword` field rather than the `"group"` literal, which is the version that cannot go
stale when a third word appears.

## `W-043` — `type network`

Topology on the **free path**, following `W-022`: the anchors still place, and the archetype supplies
only the vocabulary, the shapes and the diagnostics. A `group` is a segment, which it already was.

**A `role` picks the outline and deliberately not the fill.** `block` sets shape, fill, stroke and
ink from its kind; a topology must not, because a network diagram's colours usually already mean
something to whoever drew it — environment, tenancy, trust zone. Taking the palette would overwrite a
meaning the archetype cannot see.

`addr` is a line of the box and `speed` a bracketed line of the link, both sized like any other line:
declared and never drawn would be worse than refused.

The diagnostic worth having is a **host on no link and in no segment** — either a mistake or a fact
the diagram is failing to state. A host inside a segment counts as attached by being there, which is
what a segment means.

## `W-053` — `type venn`, and knowing what it cannot draw

Twenty-five archetypes. This one is geometry, which is why it was split out of `I-012` before being
promoted — it shares nothing with a plot frame.

**Two sets are solved.** The centre distance is found by bisection so the lens has exactly the area
written. A Venn diagram whose overlap is placed by eye is a chart lying about the one thing it exists
to show, and the lens-area formula is monotone in the distance, which is all a bisection needs.

**Three sets are arranged, not solved** — three circles cannot in general honour all seven regions at
once — and `check` says so, in a warning, rather than letting the picture imply a precision it does
not have. The numbers stay exact; the areas are indicative.

**Four is refused**, and the message names `upset` as the honest picture for that many. Refusing is
the right answer when there is no arrangement to fall back on.

Circles scale by **area**, not radius: radius would square every difference, so a set twice as big
would read as four times.

One more error worth having: an overlap larger than either set. That is a counting mistake, not a
drawing one, and no arrangement of circles could express it.

`warn_ignored` had to be split, because `venn` is the first archetype that places its own items *and*
reads edges — its overlap counts ride on them.

## `W-045` — `type harness`, and the part of it that is not built

Twenty-six archetypes. `D-025` held up exactly as written: a pin is a member line (`- 1: +12V`), a
wire is an edge carrying the pin it lands on at each end (`j1 -> j2 "power" 1 3`), and **no grammar
moved**. Both mechanisms were already there.

What the genre adds is the check: a wire must land on a pin the connector actually declares, and no
pin takes two wires. Those are the two mistakes that make a harness drawing useless to whoever is
holding the crimp tool, and they are why this is an archetype rather than a `free` diagram with boxes.

**What is not built, said plainly.** The wire joins the two *connectors*, not the two pin rows. The
mapping is stated on the line (`1 → 3`) and proved by `check`, so nothing on the page is wrong — but
the line does not touch the pin it names, which is what a WireViz drawing actually gives you. Landing
an endpoint on a row inside a box needs a per-edge endpoint offset the renderer has no notion of;
`label-offset` moves labels, not endpoints.

That is recorded as `X-016` rather than left for someone to discover. I wrote in the work order that
"a pin-to-pin mapping is not a node-and-edge graph wearing a costume" — and this delivery is, in that
one respect, exactly that. Better to name it than to let the example imply otherwise.

## `W-041` — one tree engine, three genres

Twenty-nine archetypes. `orgchart` lays the tree downward, `mindmap` outward from a central root,
`treeview` as indented rows — and they are the same placement pass read on different axes, which is
what made one engine worth writing for three genres.

**Hierarchy from edges, not from group nesting.** The work order said group nesting already existed
and `W-020` consumed it, but writing it out showed why that is wrong here: an org chart is written
`ceo -> cto`, and nesting a manager inside a group *and* declaring them as a box would be two
statements for one fact. Edges say it once.

The engine is the classic two-pass tidy tree: measure every subtree bottom-up, then hand each child a
disjoint slice of the parent's span and centre the parent over what it holds. No threads or contours,
because siblings occupy disjoint spans **by construction** — there is nothing to repair afterwards,
which is the version that stays correct when someone changes it later.

Three things stop a tree being one, and all three are reported: a second parent (the line nothing can
draw), a cycle (no root), and several roots (drawn as separate trees, with a warning saying so).

### Two guards earned their keep again

The suite refused this twice before it was right. One test caught a source using `position` under
`type treeview` — the item keyword is per-genre, so the shared test tree now uses `node`, the
universal synonym, which is itself the claim under test. The other caught **one cargo feature for
three archetypes**, which breaks `W-028`'s rule that any genre can be compiled out on its own. Three
features now, with the shared engine gated on `any(…)`.

## `W-049` — `type gitgraph`

Thirty archetypes. Commits on rails, parentage from the edges, a commit with two parents drawn as a
merge — landing one step past its **latest** parent, or the picture would show a merge arriving
before what it merges.

**Only the rails are computed.** That is the line `D-001` draws and the reason this is not `I-004`
wearing a costume: the author declares every commit, which branch it is on, and what came before it.
What the archetype supplies is the arrangement of those facts, not the facts.

A parent declared *after* its child is an error rather than a reordering. The layout numbers steps in
declaration order, so the alternative is measuring a commit against a depth that does not exist yet —
and a history diagram that runs backwards is worse than one that refuses.

Merge lines elbow rather than running diagonally across the rails: a straight diagonal over three
rails reads as touching every one it crosses.

## `W-040` — measuring text, and admitting what cannot be measured

This chantier carried a question the work order flagged and `D-026` now answers: **the SVG names a
font family and whoever renders it decides what that resolves to.** No measurement taken here can be
right by anything but luck.

The two ways to make it exact are both worse. Embedding the measured font in every SVG costs hundreds
of kilobytes a file and raises a licensing question this project has no answer to. Shipping metrics
for a fixed set of families is the same estimate with a longer table and a promise it cannot keep.

So the error was **split**, and the half that can be fixed was. The flat `0.56 × font-size` charged
`l` and `W` the same — a factor of four — and that within-typeface variation is now a per-character
advance table for a Helvetica-class sans. Non-ASCII keeps the flat guess: a Latin table has nothing
truthful to say about CJK.

One thing fell out of it that was a real bug rather than an estimate: `text_width` took the line with
the most *characters*, so the longest line and the widest line could be different lines and the box
was sized for the wrong one. It measures every line now and takes the widest.

`X-005` is **narrowed, not retired**, and its wording says why it never can be. Every checked-in
example SVG moved, which is the honest consequence of changing how everything is sized.

The suite caught one thing: a treemap test asserted that a label degrades when it does not fit, using
a label of mostly thin letters that — measured properly — now fits. The threshold moved because the
measurement got better, so the test's tile got narrower and its intent stayed.

## `W-038` — a VS Code extension, and a different failure mode

**TextMate, not WASM tree-sitter.** VS Code reads TextMate grammars natively, so nothing has to be
compiled, pinned to a revision, or invalidated from a cache — which is three of the four things that
have gone wrong with the Zed grammar. The semantic half is `bgraph-lsp` over a client the extension
launches, the same binary Zed talks to and the same front half of the compiler the CLI runs.

**The choice changes what can go wrong, so the guard changed with it.** `X-009` is about a `.scm`
query naming a node type the grammar dropped: Zed then fails to load the language and stops
recognising `.bd` files at all — loud, total, and impossible to miss. A TextMate grammar cannot name
a tree-sitter node type, so that failure is gone; what replaces it is quieter and worse to find. A
missing keyword just stops being coloured, and nobody notices for months.

So the keyword list is **re-derived from `props.rs` on every `cargo test`** rather than trusted.
Twenty-six item words and five statement keywords, checked against the tables that define them. That
is why `X-009`'s note now says `W-038` did *not* double its surface.

## `W-042` — PDF by hand, and PNG not at all

The last chantier, and the one whose scope moved once the question was asked properly.

The work order framed it as *what does the rasterising* — hand-rolled or `resvg`. Both answers are
bad: one is months of work, the other is a large dependency tree in a crate that has five. But the
question contained an assumption worth refusing. **A PDF is a vector format.** It does not need a
rasteriser at all; a content stream is `re` for a rectangle, `m`/`l`/`c` for a path and `Tj` for text
— the same size of job as the SVG writer and the watch server, both of which are hand-written here
for the same reason.

So PDF ships and PNG does not, and `D-027` says why rather than leaving a gap for someone to find.
`X-017` carries it: anyone needing a bitmap can rasterise the PDF or the SVG with a tool built for
that.

Two things worth recording:

- **The canvas is shared.** `render_svg::canvas` is now a function both writers call, so the page box
  and the viewBox cannot drift. A second implementation of the bounds would have been a second place
  for them to disagree.
- **`W-040` pays off here in a way it cannot in SVG.** A PDF viewer is required by the specification
  to have Helvetica, and the advance table added this morning *is* Helvetica's. Text measurement in
  the PDF is not an estimate — it is exact, and `X-005` does not apply to that output at all. Two
  chantiers written hours apart, and the second made the first true.

Validated with `qpdf --check` and `pdftotext` on all thirty-one examples, plus a test that walks the
cross-reference table and asserts every offset lands on the object it claims.

## `W-054` — the harness, made visual. `X-016` retired.

The Archmagos said the harness was not very visual, which is exactly what `X-016` had recorded that
morning: the wire joined the two *boxes* and stated its pins in a label.

The way in turned out to be already there. The compartment pass computes where every member row
lands in order to draw it — so it now **records** those positions, and a wire becomes a `Polyline`
from one pin row to the other, out of the shell, across, and in. A straight diagonal would have
crossed every pin between the two and read as touching them.

Recording the rows rather than recomputing them matters: a second copy of the row formula would be a
second place for the wire and the pin it names to drift apart. The pin parser is shared with `check`
for the same reason — one reading proves the pin exists, the other draws it there.

The pin pair came **off** the label. The geometry says it now, and saying it twice would be the same
fact competing with itself.

## `W-055` — the language server says what it already knew

Four capabilities, all of them things the server could answer and did not.

**Signature help.** Positional data is the idiomatic form in this language (`D-015`) and it was the
one shape nothing could tell you while you were writing it. Typing `field sport "Source port" 0 `
now shows `field <id> ["label"] <bits> <bits>` with the second `<bits>` marked as where the cursor
is. The active parameter is counted from the values already written, and clamped, so a variadic slot
keeps pointing at itself.

**Colours.** `#` is only ever a colour here (`D-004`), which is what makes a lexical scan safe — so
every literal gets a swatch and a picker, and a colour written back comes out as the shortest hex
that says it, because alpha defaults to opaque (`D-016`).

**Document highlight.** Reading a diagram means following an id around the file, and that was the
editor's find-in-file rather than anything that knew what an id is. Whole words only: `a` must not
light up inside `api`.

**Snippet completions.** Accepting `slice` used to leave you the word and the rest from memory; it
now writes `slice ${1:id} "${2:label}" ${3:value}`, with the slot named after the property it fills —
derived from `props.rs`, so a new archetype's form is right without anyone writing it out.

Hover gained two answers as well: an archetype's own word — the one you are least likely to be sure
of — reports its positional form, and a node reports the **paint the cascade settled on**, which is
four layers deep and was previously visible only by rendering the file.

## `W-056` — packaging the VS Code extension

A VSIX is a zip holding three things: the extension under `extension/`, an OPC content-types part,
and a manifest VS Code reads to decide what it has been handed. So `package.sh` builds one with
`zip`, rather than fetching `@vscode/vsce` off a registry — the same call this project already makes
for its SVG writer, its HTTP server and its PDF writer.

**Every fact the manifest repeats is read back out of `package.json`** — name, version, publisher,
engine range — and a test fails if any of them is written down twice. The engine range was hardcoded
in the first draft, which is exactly the drift this project keeps finding.

`--no-server` builds a highlighting-only package with no npm and no network. That is only a real
option because `src/extension.js` now requires the language client **inside** `activate` rather than
at the top of the file: a missing module at import time would take the whole extension down and leave
`.bd` files looking like plain text for a reason nobody could see. It says so once instead.

Verified both ways — 468 KB with the client bundled (353 files), 6 KB without — with the manifest and
every JSON part parsed back out of the archive.
